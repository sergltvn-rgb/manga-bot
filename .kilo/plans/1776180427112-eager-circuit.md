# План устранения багов и недоработок

## 1. Система денег и новые команды (Экономика/Игры)
### `cmd_rob` (Ограбление)
*   **Проблема:** Штраф при неудачном ограблении (`balance - 100`) может увести баланс инициатора в минус, так как SQLite по умолчанию не блокирует отрицательные значения.
*   **Проблема 2:** Если цель ограбления (жертва) написала сообщение очень давно (до внедрения БД) и её нет в таблице `users_stats`, `UPDATE` завершится вхолостую (0 affected rows), но бот выдаст успешное/неуспешное ограбление. То же самое касается инициатора.
*   **Решение:**
    *   Добавить `INSERT OR IGNORE INTO users_stats` для `initiator.id` и `target.id` перед операциями (или использовать общую функцию `ensure_user`).
    *   Применять штраф через безопасный запрос: `UPDATE users_stats SET balance = MAX(0, balance - 100) WHERE user_id = ?`.

### `cmd_lootbox` и `cmd_shop` (Покупки и лутбоксы)
*   **Проблема:** Гонка состояний (race condition). Бот сначала читает баланс в Python (`balance < 300`), а затем списывает `UPDATE ... SET balance = balance - 300`. Если быстро отправить несколько запросов (особенно через callback-кнопки магазина), баланс уйдет в минус.
*   **Решение:** Добавить условие прямо в SQL-запрос списания: `UPDATE users_stats SET balance = balance - 300 WHERE user_id = ? AND balance >= 300`. Если `cursor.rowcount == 0`, выводить ошибку "Недостаточно средств". Это же применить для `shop_process_title` (снятие 500 монет).

### `cmd_ref` (Реферальная система)
*   **Проблема:** В `cmd_start` проверка нового пользователя (`is_new_user`) опирается на `stats[0] == 0`, что соответствует полю `hugs` (объятия). Это ненадежный признак нового пользователя. Если реферер (пригласивший) сам ни разу не писал боту (и его нет в БД), начисление ему награды через `UPDATE` не сработает.
*   **Решение:**
    *   Перед `UPDATE` баланса реферера делать ему `INSERT OR IGNORE`.
    *   Пересмотреть проверку "новорега", возможно, проверять `messages_count <= 1` (с учетом того, что текущий /start уже засчитан middleware).

## 2. Читалка (WebApp Reader)
### Сохранение прогресса чтения (`handle_progress_post` в `bot.py` и `reader.js`)
*   **Проблема 1:** При переходе между главами или если структура данных не успела инициализироваться, `currentChapters[currentChapterIdx]?.chapter` может вернуть `undefined`. В результате на сервер отправится строка "undefined", которая сохранится как ключ главы.
*   **Проблема 2:** В читалке позиция восстанавливается через `setTimeout` (строка 145 в `reader.js`): `scrollTop = pctToRestore * maxScroll`. Однако картинки загружаются асинхронно, и высота страницы (`scrollHeight`) может значительно увеличиться после этого тайм-аута. Процент скролла применится к еще маленькому контейнеру, и юзер окажется не там, где остановился.
*   **Решение:** 
    *   **JS:** Добавить проверку на валидность ключа главы перед `apiFetch`. Заменить восстановление позиции по процентам на более надежное (либо дождаться загрузки изображений через `onload`, либо корректировать скролл с помощью `ResizeObserver`).
    *   **Python:** Добавить в `handle_progress_post` валидацию того, что `chapter_key` не является "undefined" или пустой строкой.

### API ИИ-чата читалки (`handle_ai_chat`)
*   **Проблема:** Логика извлечения `prompt` из массива `messages` уязвима. Если отправить массив без сообщений `role == 'user'` в конце, происходит либо `IndexError` (при `pop()` из пустого `history`), либо берется пустой `prompt`, что роняет сервер (status 500) вместо корректного `400 Bad Request`.
*   **Решение:** Сделать безопасное извлечение последнего `user` сообщения с проверкой длины массива `history`.

## 3. Общие мелкие недоработки
*   **Игры (рулетка, слоты, кости):** Аналогично лутбоксам, могут увести баланс в минус при быстром спаме команд из-за проверки баланса "до" снятия. Следует перевести все списания ставок на единый безопасный метод `UPDATE ... WHERE balance >= bet`.
